# تحليل اكتمال نظام الدورات في Thanawy

تاريخ التحليل: 2026-09-09
النطاق: `D:\thanawy` مع مراجعة نقاط التكامل ذات الصلة في `D:\backend`.

## الخلاصة التنفيذية

النظام يحتوي على أساس قوي لمسار الطالب: كتالوج، صفحة تفاصيل، تسجيل، دفع، مشغل فيديو، حفظ تقدم، اختبارات، مرفقات، أسئلة، تقييمات، ومؤهلات الشهادة. لذلك المشكلة ليست غياب نظام دورات، بل عدم اكتمال دورة التشغيل التجارية والتعليمية من إنشاء الدورة إلى مراجعتها ونشرها وقياسها وإدارتها بعد النشر.

أكبر خطر معماري هو وجود مسارين متوازيين:

- نموذج قديم مبني حول `Subject/Topic/SubTopic` وواجهات `/api/courses`.
- نموذج LMS أحدث في الباكند يدعم دورة حياة ومحتوى وتسعيراً وإصدارات وحزم، لكنه غير موصول بالكامل بواجهة المدرس أو بالعقود المولدة.

الترتيب المقترح للعمل:

1. إصلاح الصلاحيات وسلامة المحتوى والتحديثات المدمرة.
2. توحيد نموذج الدورة وواجهة API.
3. إكمال دورة حياة المدرس والمراجعة والنشر.
4. إكمال التجارة والشهادات والتحليلات.
5. إضافة اختبارات تكامل حقيقية ومراقبة تشغيلية.

## الفجوات المطلوبة لإكمال النظام

### P0: إصلاحات قبل الاعتماد التجاري

#### 1. توحيد التفويض في كل عمليات الاختبار

`GetCourseQuizzes` و`GetLessonCourseQuizzes` يرشحان الاختبارات المنشورة للطالب، لكن `GetCourseQuiz` يجلب الاختبار بالمعرف والدورة دون تطبيق شرط `status = published` للطالب. يجب توحيد سياسة الوصول في دالة مشتركة على جميع عمليات الجلب والبدء والإرسال والنتائج، مع اختبارات تمنع الوصول إلى اختبار مسودة أو مؤرشف.

#### 2. منع تحديث المنهج بطريقة مدمرة

`d:/backend/internal/infrastructure/api/handlers/protected/teaching_courses_handler_update.go` يحذف جميع `Topic` المرتبطة بالدورة عند إرسال `chapters` ثم يعيد إنشاءها. هذا يهدد:

- معرفات الفصول والدروس.
- التقدم والملاحظات والأسئلة والمرفقات المرتبطة بالمعرفات.
- الروابط الخارجية وسجل التغيير.
- سلامة تعديل دورة منشورة.

المطلوب API تفصيلي للإنشاء والتعديل والحذف وإعادة الترتيب، أو نظام إصدار immutable ينشر نسخة جديدة دون تعديل نسخة الطلاب الحالية. يجب عدم السماح بالتحديث المدمّر على دورة منشورة دون تأكيد ونشر نسخة.

#### 3. منع النشر المباشر خارج سير المراجعة

واجهة المدرس تعرض `published/draft/archived` فقط، وتتيح خيار `نشر فوري`. الباكند الجديد يحتوي `under_review/rejected` ومراجعات وملاحظات واعتماد، بينما واجهات CRUD القديمة تقبل النشر مباشرة. يجب فرض قاعدة واحدة على مستوى الخدمة، لا على مستوى الواجهة فقط:

`draft -> submitted -> under_review -> approved/published` أو `rejected -> draft`.

يجب تسجيل من راجع، ومتى، وسبب الرفض، وما الذي تغير قبل إعادة الإرسال.

#### 4. حماية المحتوى والمسارات غير المنشورة

يجب مراجعة كل مسارات عرض HTML في صفحة التفاصيل ومركز التعلم والمرفقات والترجمات، والتأكد من تطبيق التنقية قبل كل render. يجب أن تكون الصلاحية على الخادم هي المصدر النهائي، مع عدم الاعتماد على إخفاء العناصر في الواجهة.

### P1: توحيد المنتج والـ API

#### 5. اختيار نموذج دورة واحد وخطة ترحيل

يوجد توازي بين `Subject` القديم و`LmsCourse` الحديث في الباكند، مع اختلافات محتملة في:

- الهوية والمعرفات.
- حالات الدورة.
- المنهج والفصول والدروس.
- الأسعار والتسجيل.
- الشهادات والتقييمات.

المطلوب تحديد مصدر حقيقة واحد، ثم:

- جدول mapping رسمي مؤقت إن كان الترحيل تدريجياً.
- منع إنشاء بيانات جديدة في المسار القديم بعد نقطة محددة.
- ترحيل القراءة ثم الكتابة ثم حذف المسار القديم.
- توثيق سياسة توافق المعرفات والكاش.

#### 6. توسيع العقود المولدة

`packages/contracts/swagger.json` و`src/generated/api.ts` لا يغطيان سطح نظام الدورات بالكامل. اختبار العقد الحالي يدقق في عدد محدود من المسارات ويمكن أن يتجاوز غياب Swagger. المطلوب:

- إدراج التسجيل والتقدم والدروس والاختبارات والتقييمات والأسئلة والشهادات والتعليم والتسعير والإصدارات والحزم.
- توليد الأنواع من مصدر الباكند في CI.
- جعل فشل اختلاف العقد مانعاً للدمج.
- استبدال الطلبات اليدوية غير الموصوفة بعملاء typed تدريجياً.

#### 7. فصل صلاحيات الطالب والمدرس والمدير

يجب تعريف مصفوفة صلاحيات لكل عملية:

- قراءة دورة منشورة.
- معاينة درس مجاني.
- قراءة دورة مسودة.
- تعديل دورة يملكها المدرس.
- إرسال للمراجعة.
- اعتماد أو رفض.
- إدارة السعر والشهادة والإصدار.
- الوصول إلى محاولات الاختبارات وبيانات الطلاب.

يجب اختبار الصلاحيات في الخدمة نفسها، وليس فقط في route middleware.

### P1: التجارة والوصول

#### 8. إكمال نموذج التسعير

واجهة المدرس ترسل رقماً بسيطاً `price`، بينما الباكند يدعم تسعيراً أكثر غنى. المطلوب دعم:

- مجاني، شراء مرة واحدة، اشتراك.
- العملة والضريبة.
- السعر قبل الخصم وبعده.
- فترة الخصم وتاريخ البداية والنهاية.
- ربط خطة الاشتراك.
- سياسات الاسترداد والإلغاء.
- Webhook idempotency ومطابقة الدفع مع التسجيل.
- حالات الدفع الفاشل والمعلّق والنزاع.

#### 9. الحزم والعروض

الباكند يحتوي مسارات الحزم، لكن لا تظهر دورة الحزمة في واجهة الطالب أو المدرس. يجب إضافة إنشاء الحزمة وإدارتها، إضافة وإزالة الدورات، السعر، الأهلية، التسجيل الجزئي، والتعامل مع إلغاء دورة من الحزمة.

#### 10. التسجيل والوصول

ينبغي توثيق قواعد الوصول بوضوح: ماذا يحدث عند انتهاء الاشتراك، الاسترداد، إلغاء الدورة، حذف الحساب، أو تحديث نسخة الدورة. يجب منع التسجيل المكرر وجعل العمليات idempotent.

### P1: المحتوى والتقييم

#### 11. إكمال محرر المحتوى

المحرر الحالي يرسل شجرة المنهج كاملة، بينما الباكند يدعم عمليات أكثر دقة. يجب إضافة:

- محرر أقسام ودروس مستقل.
- سحب وإفلات مع حفظ ترتيب ذري.
- حفظ تلقائي ومسودات محلية واسترجاع.
- رفع فيديو آمن مع معالجة وتحويل وترجمة وصورة مصغرة.
- حالات معالجة الوسائط وفشلها وإعادة المحاولة.
- ربط المرفقات بالدرس مع فحص النوع والحجم والصلاحية.
- دروس مباشرة، مقالات، ملفات، واجبات وروابط بطريقة موحدة.

#### 12. الواجبات والتقييمات المتقدمة

الباكند يدعم assignments وربطها بالدروس، لكن واجهة المدرس لا تعرض دورة كاملة للواجب: إنشاء، rubric، تسليم، تصحيح، إعادة تسليم، ملاحظات، ومواعيد نهائية. يجب فصل quiz عن assignment في النموذج وتجربة المستخدم.

#### 13. توحيد نموذج الاختبار

الواجهة تحتوي `quiz` و`quizzes`، بينما المسار الخلفي يفرض اختباراً واحداً لكل درس في بعض العمليات. يجب تحديد العلاقة الرسمية، ثم إضافة قيود schema وواجهة تمنع حالات متعددة غير مدعومة، مع دعم واضح لمحاولات الإعادة والوقت والتصحيح اليدوي عند الحاجة.

### P1: الشهادات

صفحة التفاصيل تعرض أهلية الشهادة ومعاينة، لكن يجب إكمال:

- إصدار الشهادة عند تحقق شروط الإكمال.
- قائمة شهادات الطالب.
- تنزيل PDF ثابت ومؤمّن.
- صفحة تحقق عامة برقم/QR غير قابل للتخمين.
- إبطال الشهادة وسجل الإبطال.
- قالب عربي/إنجليزي وبيانات المدرس والدورة ونسختها.
- منع إصدار شهادة مرتين لنفس التسجيل إلا بسياسة واضحة.

### P2: تجربة الطالب

- إظهار الدروس المقفلة كمعطلة في القائمة بدلاً من السماح بالنقر ثم اكتشاف المنع بعد الطلب؛ `LearningHubSidebar.tsx` يعرض `locked` لكنه لا يمنع `navigateToLesson`.
- إضافة ترقيم أو infinite scroll للكتالوج بدلاً من الاعتماد على `limit=48` فقط.
- توحيد حالة التقدم بين localStorage والخادم ومعالجة تعارض الأجهزة.
- توضيح آخر درس، نسبة الإكمال، الدروس المطلوبة، وشروط الشهادة.
- دعم استكمال التنزيل أو القراءة دون اتصال بسياسة حقوق واضحة إن كان مطلوباً.
- تحسين الوصول: لوحة مفاتيح، قارئ شاشة، captions، سرعة تشغيل، اختصارات، وRTL كامل.
- إضافة إشعارات حقيقية للتسجيل، قرب الموعد، نشر درس، التصحيح والشهادة.

### P2: لوحة المدرس والتشغيل

- طابور مراجعة للدورات مع التعليق والاعتماد والرفض.
- سجل نشاط وتغييرات وإصدارات واسترجاع.
- تحليلات حقيقية: بدء الدرس، المشاهدة، التسرب حسب الدرس، الإكمال، نجاح الاختبارات، الوقت، ومصادر التسجيل.
- تقارير الطلاب مع فلاتر وتصدير وصلاحيات حماية للبيانات.
- إيرادات ومعاملات وتسويات واستردادات موثوقة.
- إدارة عدة مدرسين للدورة وأدوار المحرر والمراجع.
- استكمال الرسائل والتقويم والإشعارات بدلاً من حالات النجاح الفارغة أو بيانات placeholder.
- إعدادات SEO: slug ثابت، canonical، schema.org، صورة اجتماعية، وحالة فهرسة للدورات المنشورة فقط.

## الاختبارات المطلوبة

### اختبارات خلفية

يجب إضافة اختبارات تكامل وقاعدة بيانات تغطي:

- دورة حياة الدورة كاملة.
- صلاحيات المدرس والطالب والمدير.
- منع الوصول إلى المسودات والاختبارات غير المنشورة.
- التسجيل المكرر، الدفع المتكرر، والاسترداد.
- حفظ التقدم من جهازين وتعارض التحديثات.
- إرسال الاختبار، انتهاء الوقت، المحاولات، وإعادة المحاولة.
- عدم فقدان معرفات الدروس عند إعادة الترتيب.
- التزامن عند تعديل دورة منشورة.
- إصدار الشهادة والتحقق منها.
- التسعير والخصومات وWebhooks idempotency.

### اختبارات الواجهة وE2E

- زائر يتصفح ويفتح معاينة مجانية.
- طالب يسجل ويدفع ويفتح أول درس.
- طالب يعود من آخر نقطة على جهاز آخر.
- طالب يحاول درساً مقفلاً.
- طالب يبدأ اختباراً ويستأنفه وينتهي وقته.
- طالب يكمل الدورة ويحصل على الشهادة.
- مدرس ينشئ دورة ويحفظها كمسودة.
- مدرس يرسلها للمراجعة ويتعامل مع الرفض.
- مراجع يعتمد الدورة.
- تعديل درس منشور لا يفقد تقدم الطلاب.
- دورة خاصة لا تظهر في الكتالوج العام.

## خطة تنفيذ عملية

### المرحلة 0: أسبوع الحماية

- إصلاح فلتر الاختبارات في كل مسارات الطالب.
- إضافة اختبارات authorization للمحتوى والاختبارات.
- تعطيل النشر المباشر أو تقييده مؤقتاً إلى دور مصرح.
- منع التحديث المدمّر للدورات المنشورة.
- فحص جميع مسارات HTML والمرفقات.

### المرحلة 1: توحيد العقد والنموذج

- اعتماد نموذج LMS أو Subject بقرار رسمي.
- توسيع Swagger وتوليد العقود في CI.
- إنشاء طبقة adapter واحدة مؤقتة.
- توحيد حالات الدورة والتسجيل والتقدم.

### المرحلة 2: إكمال إدارة الدورة

- workflow المراجعة والنشر.
- محرر منهج تفصيلي وإصدارات.
- تسعير واشتراكات وحزم.
- assignments والشهادات.
- عدة مدرسين وصلاحياتهم.

### المرحلة 3: الجودة والتشغيل

- E2E للرحلة التجارية والتعليمية.
- اختبارات ضغط للتقدم والفيديو والكتالوج.
- Observability: logs مترابطة، metrics، traces، تنبيهات فشل الدفع والوسائط.
- نسخ احتياطي واسترجاع وتجربة rollback لإصدارات المحتوى.
- مراجعة أمنية خارجية لمسارات المحتوى والدفع ورفع الملفات.

## معايير اعتبار النظام متكاملاً

يعتبر النظام جاهزاً عندما:

- لا يوجد مساران متعارضان لإنشاء أو نشر الدورة.
- كل عملية قراءة أو كتابة موصوفة بعقد typed ومغطاة باختبار صلاحية.
- تعديل المنهج لا يفقد تقدم الطلاب ولا يغيّر محتوى نسخة منشورة بأثر غير مقصود.
- الدفع والتسجيل والاسترداد idempotent وقابل للتدقيق.
- الطالب يستطيع إكمال المسار واختباراته وشهادته دون تدخل يدوي.
- المدرس يستطيع الإنشاء والمراجعة والنشر والتحليل وإدارة الطلاب.
- المدير يستطيع المراجعة والاعتماد والإصدارات والحزم والقوالب.
- توجد اختبارات E2E للرحلة الأساسية ومراقبة لما بعد النشر.

## ملاحظة عن جودة القياس الحالي

نجاح type-check وESLint واختبارات الواجهة العامة لا يثبت اكتمال نظام الدورات. الاختبارات الحالية تغطي أجزاء مساعدة وتكاملات محدودة، بينما الرحلات الحساسة للتسجيل والتقدم والاختبارات والنشر والصلاحيات تحتاج اختبارات مخصصة مع قاعدة بيانات أو بيئة API حقيقية.
